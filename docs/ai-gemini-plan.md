# AI基盤をGeminiに寄せる計画

**ステータス：完了（実キーでの疎通確認まで実施済み）。** §1 の「現状」列は移行前の記録として残す。

**方針：画像生成はやらない。AIの出力は文字だけ。**
画像の上の矢印・マーカーは、MVPで作った既存の仕組み（AIが座標を返し、こちらのシステムが描画する）を
そのまま使う。詳細は §3。

---

## 1. 背景

AIの経路が2系統に割れている。

| 用途 | 現状 | 実API疎通 |
|---|---|---|
| ToC 収納提案の解析（`/api/analyze`） | OpenAI 直 `gpt-4o` | **なし**（テストは全てモック） |
| ToC 完成イメージ画像の生成（`src/lib/result-image.ts`） | OpenAI 直 `dall-e-3` | **なし**（同上） |
| マーカー自動提案（`/api/ai/suggest-b`・`suggest-c`） | OpenRouter `google/gemini-2.0-flash-exp:free` | **なし**（キー名不一致） |

3機能とも実APIには一度も接続していない。ローカルの `.env.local` には `OPENAI_API_KEY` も
`OPENROUTER_API_KEY` も無く、代わりにコードがどこからも参照していない `GEMINI_API_KEY` /
`GEMINI_MODEL` が置かれている。つまり「未検証」であって「動いていたものが壊れた」ではない。

移行の狙いは2つ。

1. **コスト** — MVPかつWoZ運用の段階で従量課金を抱えたくない。無料枠のテキストモデルで足りる。
2. **経路の一本化** — OpenAI 直と OpenRouter の2経路を保守する理由が無い。

## 2. 【対応済み】移行前のモデルは提供終了していた

調査で判明した最優先事項。

- `gemini-2.0-flash` は **2026-06-01 に非推奨**（Google 公式の料金ページ記載）。
- OpenRouter のモデル一覧に **`google/gemini-2.0-flash-exp:free` はもう存在しない**。

つまりマーカー自動提案は、キーを設定しても現状のモデル名では動かない。
移行の有無にかかわらずモデル名の差し替えが必要。

**移行先：`gemini-3.6-flash`（無料枠あり・画像入力対応）。**
ただし経路は OpenRouter ではなく Google の API 直になる。理由は §2-1。

### 2-1. OpenRouter には無料の Gemini テキストモデルが無い

OpenRouter のモデル一覧（`/api/v1/models`）で `:free` のモデルを全件確認したところ、
**`google/gemini-*` のテキストモデルは1件も無い**。`:free` に残る Google 系は
`google/gemma-4-31b-it:free` などの Gemma（オープンモデル）と、画像生成系のみ。

無料の Gemini は **Google AI Studio の API 直**にしか存在しない。したがって：

| 方針 | 経路 | キー | 評価 |
|---|---|---|---|
| **A. Gemini直（採用）** | `generativelanguage.googleapis.com` | `GEMINI_API_KEY` | 無料枠あり。`.env.local` に既にキーがある |
| B. OpenRouterでGemma | OpenRouter | `OPENROUTER_API_KEY` | 無料・画像入力可だがGeminiではない |
| C. OpenRouterで有料Gemini | OpenRouter | `OPENROUTER_API_KEY` | 従量課金。今回の目的に反する |

**A を採用。** `.env.local` にあってコードから参照されていなかった `GEMINI_API_KEY` /
`GEMINI_MODEL` が、この方針でそのまま生きる（デッド変数ではなくなる）。
新しいシークレットの発行も不要。

Google は OpenAI 互換エンドポイントも提供しているため、`/api/analyze` の OpenAI SDK は
`baseURL` とモデル名の差し替えで済む可能性がある。実装時に確認する。

## 3. 画像の上のマーカーは既存の仕組みを使う

**AIに画像を作らせない。AIは座標と文字を返すだけで、描画はこちらのシステムが行う。**

これは新規実装ではなく、既に `/api/ai/suggest-b` で動いている方式そのもの。
プロンプトが以下の形式を要求し、レスポンスをパースして保存・描画している。

```json
[
  { "x": 0.3, "y": 0.5, "category": "safety", "comment": "..." },
  { "x": 0.6, "y": 0.3, "category": "flow",   "comment": "..." }
]
```

`x` / `y` は写真上の位置を 0〜1 の比率で表す（左上が 0,0・右下が 1,1）。
パースは `parseMarkerArray()`（`src/lib/ai-markers.ts`）が担当し、モデルがコードフェンスや
補足文を付けてきても配列を取り出せるよう複数の候補を試す作りになっている。
配列として解釈できなければ空配列を返し、呼び出し側は0件として扱う。

描画側は `AdminPanel.tsx` / `BAdminPanel.tsx`（管理者の確認・修正）と
`b/report/[id]` / `demo/waiting/[id]`（閲覧）に既にある。

**この方式の利点**（画像生成と比べて）

- 座標が構造化データとして残るので、管理者が後から位置や文言を修正できる。生成画像は修正できない。
- 元写真がそのまま残る。ユーザーが撮った現場と1対1で対応する。
- テキストモデルの無料枠だけで完結する。画像生成の課金・枠制限を考えなくてよい。
- 出力がJSONなので検証可能。パース失敗を0件として安全に落とせる（既に実装済み）。

**ToC 側（`/api/analyze`）もこの方式に揃える。** 現状の「完成イメージ画像」に相当する視覚的な
表現は、元写真の上のマーカーで代替する。

### 3-1. 画像を自前で取得することの副作用（SSRF）と対策

Geminiが公開URLを取りに行かない以上、画像はこちらのサーバーが取得するしかない。
これは移行前には無かった性質で、`POST /api/analyze` は**未認証で叩ける**
（`src/proxy.ts` の matcher からも除外されている）ため、対策しないと
「任意のURLをサーバーに取りに行かせる」踏み台になる。

`src/lib/gemini.ts` で以下3点を課している。

- **オリジン制限**：`NEXT_PUBLIC_SUPABASE_URL` と同一オリジンのURLしか取得しない。
  実際に渡ってくるのは自分の Supabase Storage の公開URLだけなので、これで足りる。
  ローカル開発の http Supabase も通るよう、スキームではなくオリジンで判定している。
- **リダイレクト不追従**（`redirect: "error"`）：追うとオリジン制限を迂回されるため。
- **タイムアウト**（15秒）：応答しないホストにワーカーを占有されないため。

サイズ上限（1枚7MB）は、ボディを読み切ってから測るのではなく**読みながら数えて打ち切る**。
`Content-Length` は省略も詐称もできるので、事前チェックだけでは上限にならない。

## 4. 完成イメージ画像の生成は廃止する

`src/lib/result-image.ts`（`dall-e-3`）は**やめる**。理由は方針（画像生成をしない）に加えて、
現状の実装が機能の趣旨を満たしていないため。

`generateResultImage()` は `reasoning`（提案テキスト）だけを受け取り、プロンプト文字列だけで
画像を作っている。**ユーザーが撮った部屋の写真を渡していない。**

```
収納が整理整頓された部屋のイメージ図。手書き風のイラスト。改善ポイント：${reasoning}
```

出力は「どこかの綺麗な部屋のイラスト」であって、その人の部屋の After ではない。
これは実装漏れではなく `dall-e-3` の制約（`images.generate` はテキストプロンプトしか
受け取れない）。§3 のマーカー方式ならこの問題自体が発生しない。

廃止時の注意：`suggestions.result_image_url` カラムと、それを参照するUIの後始末が要る。
また `status` を `done` にする責務が `generateResultImage()` の中にあるため、
**削除するなら status 更新を呼び出し元に移すこと**（残さないと `analyzing` のまま固まる）。

## 6. 無料枠の調査結果

テキスト（画像入力可）モデルの無料枠は、この規模のMVPには十分。

- Gemini 3 Flash 系の無料枠は概ね **10 RPM / 250,000 TPM / 1,500 RPD** 程度。
  ただしこの数値は第三者記事によるもので、**公式のレート制限ページは具体値を載せず
  「AI Studio で確認せよ」としている**。実装時に AI Studio 上の実値を確認すること。
- 無料枠は **テキスト・画像入力に対応**（写真を渡す用途に使える）。
- WoZ運用（管理者が1件ずつ確認する）である以上、1日1,500リクエストに当たることは当面ない。

**注意：無料枠は「入力内容がGoogleの製品改善に利用される」条件付き。** 有料枠は明示的に
利用されない。ユーザーの部屋や工場の写真を送る以上、本番運用の前にこの条件を許容するか
判断が要る（→ §7 の未決事項）。

## 7. 決定事項（2026-08-04）

1. **無料枠のデータ利用条件は許容する。** 入力がGoogleの製品改善に使われる前提で無料枠を使う。
   将来これを許容できなくなった場合は、同じモデルのまま有料枠へ切り替えれば足りる
   （テキストモデルなのでコストは小さい）。**課金が必要になる箇所は現時点で無い。**
2. **`result_image_url` カラムと参照UIは当面残す。** 画像生成の呼び出しだけを止め、
   スキーマとUIには手を入れない。既存データも消さない。
   - `result_image_url` は今後 null のまま増える。**UI側は null を前提に表示できること**
     （既存のフォールバック表示で足りるかを実装時に確認する）。
   - 後片付けは別タスクとして切り出す。

### ⑦ 実キーでの疎通確認の結果（2026-08-05）

`.env.local` の `GEMINI_API_KEY` で実際に叩いて確認した。**3機能とも到達・応答を確認済み。**
なお `.env.local` は `GEMINI_MODEL=gemini-3.5-flash` を設定しているため、実行時のモデルは
コード既定の `gemini-3.6-flash` ではなく 3.5 になる（差し替え機構が動いていることの確認にもなった）。

- **テキストのみの呼び出し**：200、正常応答。
- **マーカー提案の経路（画像1枚をdata URI化）**：200、`finish_reason: stop`。
  0〜1の範囲に収まった座標付きのJSON配列が4件返り、`parseMarkerArray()` と同じ手順で取り出せた。
  usage は prompt 1260 / completion 282 / total 2622。
- **解析の経路（`/api/analyze` と同じプロンプト）**：200、`finish_reason: stop`。
  `reasoning` + `suggestions` のJSONを取り出せた。

**`max_tokens` は思考トークンも含めて数える。** 実測で本文394に対し思考が約730消費された
（`max_tokens: 100` だと本文が途中で切れることも確認）。打ち切られるとJSONが壊れて
`status='failed'` になるため、`/api/analyze` の `maxTokens` は 4000 にしている。
打ち切り（`finish_reason === "length"`）は原因が追えるよう `src/lib/gemini.ts` で警告ログに残す。

### 実装後のレビューで直したもの

多数のレビューエージェントを並列で走らせ、指摘を別のエージェントに反証させた結果、
反証を生き延びた4件を修正した。

1. **未認証のSSRF（高）** — §3-1 の対策を追加。移行によって新しく生まれた経路だった。
2. **サイズ上限が事後判定（中）** — 読みながら数えて打ち切る方式に変更（§3-1）。
3. **`/api/analyze` のJSONパースが厳格すぎる（中）** — `response_format: json_object` が
   移行で外れたのに素の `JSON.parse` のままだった。モデルが前置きを付けると
   `status='failed'` が確定保存され、リトライ経路も無いままユーザーに失敗が見える。
   マーカー提案と同じ `jsonCandidates()` を使う寛容なパースに統一した。
4. **READMEの記述漏れ（低）** — 冒頭が OpenAI / OpenRouter のままだった。

テスト側の指摘も2件取り込んだ（全画像スタブが同じバイト列で並び順を検証できていなかった点、
`maxTokens` を検証していなかった点）。

## 9. この計画で変わらないこと

- WoZ運用が主で、AIは管理者の入力補助・自動提案という位置づけ。
- APIキーが未設定でも、管理者が手動でマーカーを打つ運用は成立する。
- 解析は `/demo` から非同期でキックし、結果は `/demo/waiting/[id]` で待つ構成。
- マーカーの座標形式（0〜1の比率）と `parseMarkerArray()` によるパース。
