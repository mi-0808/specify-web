# Specify レシピ MVP 設計書

[企画書](specify-recipe-plan.md) の「部屋のレシピ」を、最小の形で動かすための設計。
見た目と操作は [デザイン規約](design-guidelines.md) に従う。

---

## 1. MVP で確かめること

> **レシピを見た人が、実際に1点目を買うか。**

そのために、MVP では次の2つだけを作る。

1. **レシピを見せる**（雰囲気 → 予算 → レシピ）。ログインは不要。
2. **保存して、「買った」を記録して、次の一手を出す**。ここから会員登録が必要。

入口からレシピを見るところまでは、会員登録なしで使える。気に入ったレシピを保存する、買った物を記録して部屋をブラッシュアップしていく、という段階で会員登録してもらう。

写真での記録は、MVP では作らない（7章）。

## 2. 画面と URL

| パス | 画面 | ログイン | 描画 |
|---|---|---|---|
| `/` | トップ | 不要 | 静的 |
| `/start` | 雰囲気を選ぶ | 不要 | 静的 |
| `/start/[style]` | 予算を選ぶ | 不要 | 静的（`generateStaticParams`） |
| `/recipes/[id]` | レシピ | 不要（「買った」を付けるときだけ必要） | 動的（ログイン中は記録を読むため） |
| `/home` | ホーム（進み具合と次の一手） | 必要 | 動的 |
| `/login` | ログイン・新規登録（既存） | — | — |

画面の流れ：

```
/ ──「理想の部屋を選ぶ」──▶ /start ──雰囲気を選ぶ──▶ /start/korean ──予算を選ぶ──▶ /recipes/korean-50000
                                                                                       │
                                                                     「買った」（未ログインなら /login を経由）
                                                                                       ▼
                                                                                     /home
```

- 1画面1目的にするため、雰囲気と予算は別の画面で選ぶ。どちらもリンクを並べるだけで、フォームや JS は使わない。
- ログイン後の移動先は `/home`。
- `src/lib/supabase/proxy.ts` のログイン不要リストは `/`・`/login`・`/start`・`/recipes`。

## 3. 画面仕様

### 3-1. `/` トップ

- 今の文言に、「理想の部屋を選ぶ」の主ボタン（塗り）を足す → `/start`
- ヘッダー右上は「マイページ」（`/home`）。未ログインならログイン画面へ送られる。ログイン状態を読まずに済むので、ページを静的に保てる。

### 3-2. `/start` 雰囲気を選ぶ

- 雰囲気ごとに、見本の写真・名前・一言説明のカードを並べる。カード全体が `/start/[style]` へのリンクになる。
- 最初は3つ：韓国風・北欧ナチュラル・カフェ風（企画書0章の仮説）。

### 3-3. `/start/[style]` 予算を選ぶ

- 上に、選んだ雰囲気の写真と名前を表示する。
- 予算帯ごとにリンクを並べる：「3万円で」「5万円で」「10万円で」→ `/recipes/[id]`
- レシピがまだない予算帯は、リンクにせず「準備中」と表示する。

### 3-4. `/recipes/[id]` レシピ

| 要素 | 内容 |
|---|---|
| 見出し | 雰囲気の名前と予算（例：「韓国風・5万円」） |
| 総額 | 商品価格の合計と、予算の残り（例：「合計 ¥46,800（あと ¥3,200）」）。「◯月◯日時点の価格」と添える |
| 商品の一覧 | 買う順に並べる。1行に、順番・役割（ラグ、照明など）・商品名・店・価格・ひとこと（なぜこれを買うか）を表示する |
| 商品ページへのリンク | 店の公式サイトを新しいタブで開く。新しいタブで開くことは、アイコンと読み上げ用の文言で伝える |
| 保存ボタン | 総額の下に置く。ログイン中は「このレシピを保存する」⇔「保存済み ✓」。未ログインなら「会員登録して保存する」（`/login?signup=1&next=/recipes/[id]`、新規登録の画面で開く） |
| 「買った」ボタン | ログイン中だけ各商品に付ける。押すと記録され、「買った ✓」に変わる（もう一度押すと取り消す）。買い始めたレシピは自動で保存される |

- 最初の1行は「最初の1点」として強調する（primary-container のカード）。安く始めたいターゲットに、まず1つ買ってもらうため。
- 商品の画像は載せない。各社の商品写真は各社の著作物なので、無断で転載しない。見た目はリンク先で確認してもらう。

### 3-5. `/home` ホーム

- 保存したレシピごとに、次を表示する：
  - 進み具合：「5点中2点」、使った金額
  - **次の一手**：まだ買っていない商品のうち、いちばん順番が早いもの（役割・商品名・店・価格・リンク）
  - 全部買い終わったら、「このレシピは完成です」と表示し、`/start` への導線を出す
- 1つも記録がないときは、「まずはレシピを選びましょう」と表示し、`/start` へのボタンを置く。

## 4. データ

### 4-1. レシピ：コードの中に持つ

レシピは `src/data/recipes.ts` に TypeScript で書く。Supabase には置かない。

- レシピを作るのは開発者本人なので、管理画面は要らない。
- 静的なデータなので、ページを静的に生成でき、表示が速い。
- 価格を更新したら、コミットしてデプロイし直す。
- 編集する人が開発者以外に増えたら、Supabase のテーブルに移す。

```ts
export type StyleId = "korean" | "nordic" | "cafe"

export type Style = {
  id: StyleId
  name: string          // 「韓国風」
  description: string   // 一言説明
  image: string         // public/styles/ 以下のパス
}

export type Shop = "nitori" | "ikea" | "muji" | "3coins"

export type RecipeItem = {
  id: string            // レシピ内で一意（例："rug"）。記録のキーになるので、一度決めたら変えない
  role: string          // 部屋での役割（「ラグ」「照明」）
  name: string          // 商品名（店の表記どおり）
  shop: Shop
  price: number         // 税込・円
  url: string           // 店の公式商品ページ
  reason: string        // なぜこれを買うか（一言）
  checkedAt: string     // 価格・在庫を確認した日（YYYY-MM-DD）
}

export type Recipe = {
  id: string            // `${style}-${budget}`（例："korean-50000"）
  style: StyleId
  budget: 30000 | 50000 | 100000
  items: RecipeItem[]   // 買う順
}
```

- 総額は保存せず、`items` の価格の合計を計算して出す。
- 「賃貸で使える」「6〜8畳に収まる」は、データには持たせない。レシピを作るときのチェック項目にする（6章）。

**データの整合性テスト**（`src/data/recipes.test.ts`）

次のどれかが崩れたら、テストを失敗させる。
- レシピ ID と、レシピ内の商品 ID が重複していない
- 総額が予算以下になっている
- URL が `https://` で始まり、その店の公式ドメインになっている
- `checkedAt` が正しい日付になっている
- 参照している雰囲気が実在する

### 4-2. 「買った」の記録：Supabase

テーブルを2つ追加する（`supabase/migrations/20261015120000_create_purchases_and_saved_recipes.sql`）。`saved_recipes`（保存したレシピ）と `purchases`（買った商品）。旧企画の `items` テーブルと名前がぶつからないように、`purchases` にする。

```sql
create table public.purchases (
  user_id uuid not null references auth.users(id) on delete cascade,
  recipe_id text not null,
  item_id text not null,
  created_at timestamptz not null default now(),
  primary key (user_id, recipe_id, item_id)
);

alter table public.purchases enable row level security;

create policy "本人の記録だけ読める" on public.purchases
  for select using (auth.uid() = user_id);
create policy "本人の記録だけ追加できる" on public.purchases
  for insert with check (auth.uid() = user_id);
create policy "本人の記録だけ消せる" on public.purchases
  for delete using (auth.uid() = user_id);
```

- `recipe_id` と `item_id` は、コード内のレシピの ID を入れる。DB 側からは参照先を確認できないため、書き込む前にサーバー側で確認する（5章）。

## 5. 処理：「買った」の切り替え

API ルートは作らない。Next.js の Server Action を2つ使う（`toggleSave` と `togglePurchase`）。

`togglePurchase(recipeId, itemId)`（`src/app/recipes/[id]/actions.ts`）

1. ログイン中のユーザーを取得する。未ログインなら何もしない。Server Action は画面を通さず直接呼べるので、必ず中で確認する。
2. `recipeId` と `itemId` が `recipes.ts` に実在するか確認する。なければ何もしない。
3. 記録があれば削除し、なければ追加する。
4. `revalidatePath` で、`/recipes/[id]` と `/home` を表示し直す。

- ボタンは `<form action={togglePurchase}>` の中に置く。JS が読み込まれる前でも動く。
- 処理中は、ボタンに `aria-busy` とインジケーターを出す（デザイン規約 4章）。

## 6. 実装順序

| 順 | 作業 | 終わったらできること |
|---|---|---|
| 1 | `recipes.ts` の型と、レシピを1つ（韓国風・5万円）。整合性テストも書く | — |
| 2 | `/recipes/[id]`（「買った」ボタンなし） | **レシピを見せてインタビューできる** |
| 3 | `/start`、`/start/[style]`、トップの主ボタン | 雰囲気から選んでもらえる |
| 4 | `purchases` テーブルと「買った」ボタン | 記録できる |
| 5 | `/home`、ログイン後の移動先 | 次の一手が出る |
| 6 | 残りのレシピ（3雰囲気 × 3予算） | — |

- 2 が終わった時点で、ターゲットの人3〜5人にレシピを見せる。「1点目を買う」と言ってもらえなければ、4 以降に進む前にレシピの中身を見直す。
- 各ページを、作った時点で `src/app/a11y.test.tsx` に追加する。

### レシピを作るときのチェック項目

- [ ] 壁に穴を開けずに使える（賃貸でも使える）
- [ ] 6〜8畳の部屋に置ける大きさ
- [ ] 公式サイトで在庫があり、価格を確認した（`checkedAt` を更新した）
- [ ] 1点目だけでも雰囲気が変わる順番になっている
- [ ] 総額が予算以下

## 7. MVP でやらないこと

| やらないこと | 入れる条件 |
|---|---|
| 写真での記録（届いた家具を撮る） | 「買った」の記録が使われていると確認できたら |
| SNS の画像から商品を特定する | 手で作ったレシピで、課題が解けると確認できたら |
| レシピの管理画面 | 開発者以外がレシピを作るようになったら |
| 価格の自動更新 | レシピが増えて、手で確認しきれなくなったら |
| アフィリエイトリンク | 収益化の方針を決めたら |
| 商品の画像 | 掲載の許可が取れたら |

## 8. 検証指標

| 指標 | 取り方 |
|---|---|
| 1点目を買った人の割合 | `purchases` に記録が1件以上あるユーザー ÷ 登録ユーザー |
| レシピを買い進めた数 | ユーザーごとの `purchases` の件数 |
| インタビューでの反応 | 「レシピを見て1点目を買うか」「総額を見て高いと感じたか」 |

商品リンクのクリック数はまだ取らない。必要になったら、アクセス解析の導入と合わせて検討する。
