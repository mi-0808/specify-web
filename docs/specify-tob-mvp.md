# Specify ToB MVP 仕様設計書

## 1. コンセプト

> **「現場の写真を撮って送るだけで、動線・安全の問題点が画像上のマーカーで返ってくる」**

### ターゲット像と主要ユースケース

| ユースケース | 具体的な場面 | 取り込みやすさ |
|---|---|---|
| **設備変更前後の確認** | 設備投資を控えた工場が「今の配置でいいか」を確認したい | ★★★ 予算あり・課題意識が明確 |
| **継続的な改善活動** | 月次・週次で現場を定期スキャンして改善の推移を追う | ★★★ リピートにつながる |
| **新人研修** | 「なぜこの配置か」をレポートとして教育コンテンツに使う | ★★ 需要は確実にある |

### ToCとの差異

| 項目 | ToC | ToB |
|---|---|---|
| ターゲット | 個人（自宅の収納） | 工場担当者・現場管理者 |
| 判断軸 | 使いやすさ（主観） | 動線距離・安全・5S（客観） |
| 返答の形 | テキストの提案カード | 写真上のマーカー＋コメント |
| リピート契機 | 模様替え・季節 | 設備変更・改善活動・新人研修 |

| 項目 | 決定内容 |
|---|---|

## 2. MVPフェーズ定義

### Phase 1（本仕様）：WoZ

AIは使わない。管理者（開発者）が写真を見て手動でマーカーとコメントを付け、担当者に返す。
目的は「画像上のマーカーレポートに価値があるか」の仮説検証。

### Phase 2（将来）：YOLO補助

ブラウザ内でYOLO（ONNX Runtime Web）を動かし、工具・障害物を自動検出。
管理者のマーカー打ちを補助する形で段階的に自動化。

### Phase 3（将来）：動線自動計算・Before/After

検出した物の位置から動線距離を自動算出。設備変更前後のBefore/After比較機能を追加。

## 4. 即時返信と通知の仕組み

### 担当者側のフロー

```
写真送信
  ↓
送信完了画面を表示（ローディングなし・即座に）
「ご送信ありがとうございます。レポートが完成次第、メールでお知らせします。」
「この画面は閉じていただいて構いません。」
  ↓
（管理者が対応後）レポート完成 → 担当者にメールを送信
メール本文：「レポートが届きました → [レポートを見る] ボタン（/b/report/[id] へのリンク）」
```

### 管理者側のフロー

```
新しいスキャン送信
  ↓
管理者にメール通知（件名：「[Specify] 新しいスキャンが届きました」）
メール本文：エリア名、送信者、/b/admin へのリンク
  ↓
管理者が /b/admin を開いて対応
```

### メール送信の実装方針（MVP）

Supabase の Edge Function + Resend（無料プラン：月3,000通）を使用する。
SendGrid等でも可だが Resend が最も実装が軽い。

```typescript
// スキャン受信時 → 管理者にメール
// レポート送信時 → 担当者にメール
// どちらも同じEdge Functionを呼び出す
```

## 5. 画面仕様

### 5-1. `/b` ランディング

**要素**
- キャッチコピー：「現場の写真を撮るだけで、動線と安全の問題が見える」
- サブコピー：「動線改善・安全確認・新人研修・設備変更前後の確認に」
- 「無料で試してみる」ボタン → `/b/workspace`（未ログイン時は `/login` 経由）

---

### 5-2. `/b/workspace` エリア一覧

**要素**
- エリアカード（エリア名、最終スキャン日時、レポートステータスバッジ）
  - バッジ：`確認中`（pending）/ `レポート完了`（done）
- 「+ 新しいエリアを追加」ボタン → `/b/scan`

**状態**
- データなし：「まず現場のエリアを登録してみましょう」＋CTAボタン
- データあり：エリアカード一覧

---

### 5-3. `/b/scan` 撮影フロー

| ステップ | 要素 |
|---|---|
| `input` | エリア名入力（例：「第1工具棚」）、「次へ」 |
| `capture` | カメラ起動 or ライブラリ選択、撮影プレビュー、「この写真で送信」 |
| `sent` | 送信完了。画面を閉じてOKの案内。「エリア一覧に戻る」ボタン |

**重要**：`sent` 画面は即座に表示する（API応答を待たない）。
送信はバックグラウンドで行い、失敗時はリトライ or エラートースト。

**撮影ガイド**（`capture` ステップに表示）
- 「エリア全体が写るように、少し離れて撮影してください」
- 「明るい場所で撮影すると分析精度が上がります」

---

### 5-4. `/b/report/[id]` レポート表示

**メインUI：画像マーカービュー**

```
┌────────────────────────────────────┐
│                                    │
│   [撮影写真]                        │
│          ● 1                       │  ← マーカー（クリックでコメント展開）
│                  ● 2              │
│                                    │
└────────────────────────────────────┘

① 工具Aが通路側に出ている
  → 棚の奥側に移動することで動線が確保されます

② 消火器が棚の陰に隠れている
  → 視認できる位置への移動を推奨します
```

**マーカーの仕様**
- 番号付き円マーカー（●1, ●2 ...）
- タップ / クリックで対応するコメントをハイライト
- カテゴリ色分け（後述）

**カテゴリ色**
- 🔴 赤：安全上の問題（危険物、緊急経路の障害）
- 🟡 黄：動線の問題（余分な移動、作業効率の低下）
- 🔵 青：改善提案（5S、配置の最適化）

**状態**
- `pending`（レポート未完成）：「レポートを作成中です。完成次第メールでご連絡します。」
- `done`：マーカービュー＋コメント一覧を表示

---

### 5-5. `/b/admin` 管理者画面（重点改善）

#### 設計方針

前回のToC管理画面の反省を踏まえ、以下を優先する：
- **写真を大きく見せる**（作業の中心は写真の観察）
- **マーカーを直感的に打てる**（クリック1回でピン、すぐコメント入力）
- **送信ボタンを常に目に見える位置**（固定フッターに配置）
- **未対応件数を最初に把握できる**（バッジで明示）

#### レイアウト構成

```
┌──────────────────────────────────────────────────┐
│  [Specify Admin]              未対応: 3件 🔴      │  ← ヘッダー
├────────────────┬─────────────────────────────────┤
│                │                                 │
│  未対応一覧    │  [選択中のスキャン詳細]           │
│  ──────────    │                                 │
│  ● 第1工具棚  │  エリア名: 第1工具棚             │
│    10分前      │  送信者: ○○工場 田中様           │
│               │  送信時刻: 2026-07-08 14:32      │
│  ● 作業台B    │                                 │
│    2時間前     │  ┌────────────────────────┐    │
│               │  │                        │    │
│  対応済み一覧  │  │  [写真（大きく表示）]    │    │
│  ──────────    │  │           ● 1          │    │
│  ✓ 工具棚A   │  │                        │    │
│    昨日        │  └────────────────────────┘    │
│               │  ↑ 写真をクリックしてマーカーを追加│
│               │                                 │
│               │  マーカー一覧                    │
│               │  ┌──────────────────────────┐  │
│               │  │ ● 1  [🔴安全▼]           │  │
│               │  │ テキスト入力...            │  │
│               │  │ [削除]                    │  │
│               │  ├──────────────────────────┤  │
│               │  │ ● 2  [🟡動線▼]           │  │
│               │  │ テキスト入力...            │  │
│               │  └──────────────────────────┘  │
│               │  [+ マーカーを追加]              │
│               │                                 │
├────────────────┴─────────────────────────────────┤
│  [スキップ（後で対応）]    [レポートを送信 ✓]      │  ← 固定フッター
└──────────────────────────────────────────────────┘
```

#### マーカー追加の操作フロー

1. 写真上の任意の場所をクリック
2. 写真上にマーカー（●N）が出現
3. 右側のマーカー一覧に入力欄が追加される
4. カテゴリ（安全 / 動線 / 改善提案）を選択
5. コメントを入力
6. 「レポートを送信」で保存・担当者にメール

#### 入力補助（管理者の専門知識が薄くても使えるように）

専門知識が薄くても直感的に指摘できるよう、定型文のテンプレートを用意する。

```
カテゴリ選択時にテンプレートを提示：

[🔴 安全] を選んだ場合：
  - 「通路に物が出ており、緊急時の避難経路を妨げる可能性があります」
  - 「危険物（工具・重量物）が不安定な場所に置かれています」
  - 「消火器・AEDへのアクセスが遮られています」

[🟡 動線] を選んだ場合：
  - 「この工具の使用頻度に対して、取り出し位置が遠すぎます」
  - 「作業手順の順番と工具の配置順が逆になっています」
  - 「頻繁に使う工具と使わない工具が混在しています」

[🔵 改善提案] を選んだ場合：
  - 「定位置を決めてラベリングすると管理が楽になります」
  - 「高さを揃えると視認性が上がります」
  - 「使用頻度の高い工具を手前・低い位置に移動することを推奨します」
```

## 6. APIエンドポイント仕様

### `POST /api/b/scan`

**リクエスト**
```typescript
{
  area_name: string
  image: string       // base64
  user_id: string
}
```

**レスポンス**（即座に返す、メール送信はバックグラウンド）
```typescript
{
  scan_id: string
  status: 'pending'
}
```

**副作用**：管理者にメール通知を送信（非同期）

---

### `GET /api/b/report?scan_id=xxx`

レポート表示画面のロード時に1回だけ叩く（ポーリングしない）。

**レスポンス（pending）**
```typescript
{ status: 'pending' }
```

**レスポンス（done）**
```typescript
{
  status: 'done'
  area_name: string
  image_url: string
  markers: Array<{
    id: string
    x: number           // 写真上のX座標（0〜1のパーセンテージ）
    y: number           // 写真上のY座標（0〜1のパーセンテージ）
    category: 'safety' | 'flow' | 'suggestion'
    comment: string
  }>
}
```

---

### `POST /api/b/admin/report`

**リクエスト**
```typescript
{
  scan_id: string
  markers: Array<{
    x: number
    y: number
    category: 'safety' | 'flow' | 'suggestion'
    comment: string
  }>
}
```

**副作用**：担当者にメール通知を送信

## 7. DBスキーマ

```sql
-- エリアスキャンテーブル
CREATE TABLE b_scans (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id     uuid REFERENCES auth.users(id),
  area_name   text NOT NULL,
  image_url   text,
  status      text NOT NULL DEFAULT 'pending'
                   CHECK (status IN ('pending', 'done')),
  created_at  timestamptz DEFAULT now()
);

-- レポートマーカーテーブル
CREATE TABLE b_markers (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  scan_id     uuid REFERENCES b_scans(id) ON DELETE CASCADE,
  x           float NOT NULL,   -- 0〜1（写真幅に対するパーセンテージ）
  y           float NOT NULL,   -- 0〜1（写真高さに対するパーセンテージ）
  category    text NOT NULL CHECK (category IN ('safety', 'flow', 'suggestion')),
  comment     text NOT NULL,
  sort_order  int NOT NULL DEFAULT 0,
  created_at  timestamptz DEFAULT now()
);

-- インデックス
CREATE INDEX b_scans_user_id_idx ON b_scans(user_id);
CREATE INDEX b_markers_scan_id_idx ON b_markers(scan_id);
```

## 9. 実装順序

```
① DBスキーマ適用（b_scans・b_markers作成）
② POST /api/b/scan（スキャン受付 + 管理者メール）
③ POST /api/b/admin/report（レポート保存 + 担当者メール）
④ GET /api/b/report（レポート取得）
⑤ /b/admin 管理者画面（マーカーUI）    ← WoZ運用のため最優先
⑥ /b/scan 撮影フロー
⑦ /b/report/[id] レポート表示（マーカービュー）
⑧ /b/workspace エリア一覧
⑨ /b ランディング
```

**⑤を先にする理由**：担当者より先に管理者が使えないとWoZ自体が成立しない。

## 10. MVP対象外リスト

- YOLO・機械学習による自動物体検出
- 動線距離の自動計算
- Before/After比較（将来の設備変更ユースケース用）
- 定期スキャンのスケジューリング（継続改善ユースケース用）
- 複数ユーザー管理・テナント機能
- 料金プラン・決済
- プッシュ通知（メール通知のみ実装）

## 11. 検証指標

### 定量

- スキャン送信数
- レポートメールのクリック率（リンクを踏んでレポートを見たか）
- リピートスキャン率（同じユーザーが2回以上送信したか）

### 定性（ユーザーインタビュー時の確認点）

- 「マーカーで返ってきた時、問題の場所がすぐわかったか」
- 「このレポートを上司や同僚に共有したいと思ったか」
- 「設備変更のタイミングで使いたいと思うか」
- 「新人に現場を説明する時に使えると思うか」
```
